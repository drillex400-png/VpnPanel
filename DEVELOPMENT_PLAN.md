# PanelVPN — Полный план развития

> Цель: превратить прототип в production-ready систему управления Linux-серверами и VPN-узлами.
> Принципы: безопасность, стабильность, реальная работоспособность, никаких заглушек.

---

## ЭТАП 1 — БЕЗОПАСНОСТЬ (Критический, недели 1-2)

### 1.1 Аутентификация панели управления
**Проблема:** Express-сервер доступен без аутентификации — кто угодно может выполнить SSH-команду на любом подключённом сервере.

**Решение:**
- Реализовать JWT-аутентификацию (или сессионную) для доступа к API
- Создать сущность `AdminUser` (email, passwordHash, role)
- Первый запуск — мастер-настройка: создание администратора
- Все `/api/*` эндпоинты (кроме `/api/auth/login`) защищены middleware
- Rate limiting на логин (5 попыток / минута, экспоненциальная блокировка)
- 2FA (TOTP) как опция — интеграция с Google Authenticator

**Файлы:**
- `server.ts` → разбить на `server.ts` + `routes/auth.ts`, `middleware/auth.ts`
- Новый: `src/pages/LoginPage.tsx`, `src/pages/SetupPage.tsx`
- БД: SQLite (better-sqlite3) или встроенное хранилище для пользователей

### 1.2 Защита SSH-учётных данных
**Проблема:** Пароли и приватные ключи SSH хранятся в `localStorage` браузера в открытом виде (`saveServerProfile`).

**Решение:**
- Перенести хранение профилей серверов на бэкенд
- Шифровать SSH-пароли/ключи на бэкенде с помощью AES-256-GCM
- Ключ шифрования — мастер-пароль пользователя (PBKDF2/Argon2 derivation)
- Фронтенд хранит только JWT-токен, не SSH-креды
- Добавить сущность `ServerProfile` (id, name, host, port, username, encryptedPassword, encryptedKey, ownerId)

### 1.3 Защита API-эндпоинтов
**Проблема:** Нет rate limiting, нет валидации входных данных, нет security headers.

**Решение:**
- `express-rate-limit` на все эндпоинты:
  - `/api/ssh/exec` — 30 запросов/минута на пользователя
  - `/api/ssh/test` — 10/минута
  - `/api/ai/*` — 20/минута
  - `/api/auth/login` — 5/минута
- `helmet` для security headers (CSP, X-Frame-Options, etc.)
- `cors` — ограничить origins (только домен панели)
- `express-validator` для валидации всех `req.body`:
  - `host` — IP/домен, не дольше 255 символов
  - `port` — число 1-65535
  - `command` — строка, не длиннее 10000 символов
  - Запрет shell-метасимволов в полях, не предназначенных для выполнения

### 1.4 Санитизация SSH-команд
**Проблема:** Команды от фронтенда передаются напрямую в `exec()` / `conn.exec()` — нет фильтрации.

**Решение:**
- Whitelist разрешённых команд (или паттернов) на бэкенде
- Запрет двойного выполнения: команды собираются на бэкенде, не в строке шаблона
- Логирование всех SSH-команд (audit log): кто, когда, что выполнил, результат
- Для файловых операций — использовать SFTP API (`ssh2` supports it) вместо `cat`/`echo`/`rm`

### 1.5 Замена `alert()` на системные уведомления
**Проблема:** 18+ `alert()` вызовов по проекту — блокируют UI, не информативны.

**Решение:**
- Создать `ToastProvider` + `useToast()` hook
- Типы: success, error, warning, info
- Авто-закрытие, стек уведомлений, action-кнопки

## ЭТАП 2 — СТАБИЛЬНОСТЬ ( недели 3-4)

### 2.1 Рефакторинг бэкенда
**Проблема:** `server.ts` — 709 строк в одном файле.

**Решение — структура:**
```
server/
├── index.ts              — точка входа
├── app.ts                — конфигурация Express
├── config.ts            — env-переменные, константы
├── db/
│   ├── index.ts          — инициализация БД
│   └── schema.ts         — схема таблиц
├── middleware/
│   ├── auth.ts           — JWT-проверка
│   ├── rateLimit.ts       — rate limiting
│   ├── errorHandler.ts    — централизованная обработка ошибок
│   └── validator.ts       — валидация запросов
├── routes/
│   ├── auth.ts           — /api/auth/*
│   ├── ssh.ts            — /api/ssh/*
│   ├── servers.ts         — /api/servers/* (профили)
│   ├── vpn.ts            — /api/vpn/* (деплой, статус, конфиг)
│   └── ai.ts             — /api/ai/*
├── services/
│   ├── ssh.ts            — SSH-подключения, пул соединений
│   ├── crypto.ts          — шифрование кредов
│   └── audit.ts           — логирование действий
└── utils/
    ├── parser.ts         — парсинг Linux-вывода
    └── validator.ts      — утилиты валидации
```

### 2.2 Пул SSH-соединений
**Проблема:** Каждая команда открывает новое SSH-соединение. 4-секундный опрос метрик = ~15 соединений/минута.

**Решение:**
- `ssh2` connection pool: держать 1-2 активных соединения на сервер
- Reconnect-логика с экспоненциальной задержкой
- Heartbeat (keepalive) каждые 30 секунд
- Авто-закрытие простаивающих соединений через 5 минут
- Очередь команд на одно соединение

### 2.3 Обработка ошибок и устойчивость
**Проблема:** Ошибки SSH молча проглатываются, fallback на mock-данные скрывает реальную проблему.

**Решение:**
- Централизованный `errorHandler` middleware
- Категории ошибок: `SSHConnectionError`, `SSHErr`, `ValidationError`, `AuthError`, `AIError`
- На фронтенде — Error Boundaries на каждый view
- WebSocket для real-time статуса соединения (вместо опроса каждые 4 секунды)
- При ошибке метрик — показывать баннер "Соединение потеряно", НЕ подменять mock-данными

### 2.4 Замена polling на WebSocket
**Проблема:** HTTP-опрос каждые 4 секунды создаёт нагрузку и задержки.

**Решение:**
- `ws` (WebSocket) на бэкенде
- Бэкенд держит SSH-соединение и стримит метрики раз в 3-5 секунд
- Фронтенед подписывается на `ws://host/ws/metrics/:serverId`
- Метрики CPU/RAM/сеть собираются через одну SSH-команду, парсятся на бэкенде
- Терминал — тоже через WebSocket (интерактивный, двунаправленный)

### 2.5 Интеграционные тесты
**Проблема:** Нет тестов.

**Решение:**
- `vitest` для unit-тестов
- Мокировать SSH через тестовый контейнер (Docker с OpenSSH)
- Тесты API через `supertest`
- CI через GitHub Actions

## ЭТАП 3 — ПОЛНАЯ РАБОТОСПОСОБНОСТЬ (недели 5-8)

### 3.1 Файловый менеджер — SFTP вместо bash-парсинга
**Проблема:** Файлы читаются через `ls -la` и `cat` с парсингом строк. Хрупко, небезопасно, не работает с файлами со спецсимволами в имени.

**Решение:**
- Использовать SFTP API из `ssh2` (`sftp.readdir`, `sftp.readFile`, `sftp.writeFile`, `sftp.unlink`, `sftp.mkdir`)
- Реальные операции:
  - Чтение директории — структура с метаданными (размер, права, дата, владелец)
  - Чтение файла — с лимитом размера (макс 5 МБ)
  - Редактирование и сохранение
  - Удаление (с подтверждением для директорий)
  - Создание директорий и файлов
  - Изменение прав и владельца (`chmod`, `chown`)
  - **Загрузка файлов с клиента на сервер** (upload через SFTP)
  - **Скачивание файлов с сервера** (download через SFTP)
  - Переименование/перемещение
  - Поиск файлов по имени

### 3.2 Терминал — интерактивный PTY
**Проблема:** Терминал выполняет по одной команде, нет интерактивности (стрелки, tab, Ctrl+C, цветной вывод).

**Решение:**
- PTY через SSH (`conn.shell()`) вместо `conn.exec()`
- WebSocket-стрим: двунаправленный поток stdin/stdout/stderr
- Фронтенд: `xterm.js` (эмулятор терминала)
- Поддержка цвета (ANSI), tab-completion, стрелки, Ctrl+C/Z/D
- Несколько параллельных сессий (вкладки)
- Авто-закрытие простаивающих сессий (10 минут)
- Логирование сессии (audit) — запись ввода/вывода, доступная админу

### 3.3 VPN-модуль — реальный деплой и мониторинг
**Проблема:** Деплой генерирует bash-скрипт инлайн, статус установки не проверяется, метрики трафика — заглушки.

**Решение — разбить на бэкенд-эндпоинты:**

**A. Развёртывание (`POST /api/vpn/deploy`)**
- Бэкенд собирает скрипт установки (не фронтенд!)
- Бэкенд выполняет по шагам с логированием прогресса:
  1. Проверка системы (ОС, архитектура, наличие зависимостей)
  2. Установка бинарников (Xray/sing-box/amneziawg)
  3. Генерация ключей на сервере (`xray x25519`, `xray uuid`)
  4. Создание конфигурации
  5. Настройка файрвола (UFW)
  6. Регистрация systemd-юнита
  7. Запуск и верификация (`systemctl is-active`)
- Прогресс стримится через WebSocket
- При ошибке на любом шаге — откат (cleanup)
- Сохранение результата в БД (InstalledVPN entity)

**B. Мониторинг (`GET /api/vpn/status/:serverId`)**
- Реальные данные из сервера:
  - `systemctl is-active <service>` — статус
  - `journalctl -u <service> -n 1 --no-pager` — последние логи
  - Трафик: чтение из `/proc/net/dev` или `vnstat` (если установлен)
  - Количество клиентов: парсинг логов Xray (access log) или API 3X-UI
  - Uptime: `systemctl show <service> -p ActiveEnterTimestamp`

**C. Управление (`POST /api/vpn/:id/:action`)**
- start / stop / restart / enable / disable
- Удаление: полная очистка (бинарник, конфиг, systemd-юнит, UFW-правило)
- Обновление версии
- Просмотр и редактирование конфига (через SFTP)
- Управление клиентами (добавление/удаление UUID, лимиты)

**D. Конфигурация**
- Генерация конфига на бэкенде, не на фронтенде
- Поддержка multi-client (несколько UUID на один inbound)
- Валидация конфига перед записью (JSON schema для Xray/sing-box)
- Backup конфига перед изменением
- QR-код генерируется из реальной клиентской ссылки

### 3.4 Процессы — реальное управление
**Проблема:** Начальные данные — mock (`INITIAL_PROCESSES`). kill/renice работают, но нет обновления в реальном времени.

**Решение:**
- Убрать `INITIAL_PROCESSES` — загружать только с сервера
- Обновление каждые 5 секунд (через WebSocket)
- Сортировка по CPU/RAM
- Поиск по имени/PID
- Mass-kill (выбор нескольких процессов)
- Дерево процессов (`pstree` или парсинг `/proc/*/stat`)
- График CPU/RAM по процессу во времени

### 3.5 Сервисы — полная интеграция с systemd
**Проблема:** `INITIAL_SERVICES` — mock. Нет управления timers, нет просмотра зависимостей.

**Решение:**
- Убрать mock-данные
- `systemctl list-units --type=service --no-pager` — список
- `systemctl list-timers` — таймеры (отдельная вкладка или секция)
- `systemctl status <unit>` — детальная информация (секция "проблемы")
- `systemctl list-dependencies <unit>` — дерево зависимостей
- `systemctl cat <unit>` — просмотр/редактирование unit-файла
- `journalctl -u <unit> -f` — стриминг логов сервиса
- Управление: start, stop, restart, reload, enable, disable, mask, unmask

### 3.6 Файрвол — расширенное управление
**Проблема:** `INITIAL_FIREWALL_RULES` — mock. Базовые UFW операции есть, но нет nftables, нет app profiles.

**Решение:**
- Убрать mock-данные
- Поддержка UFW + nftables (автоопределение)
- UFW app profiles (`ufw app list`, `ufw app info`)
- Добавление/удаление правил с реальным feedback
- Просмотр активных соединений (`ss -tulpn`)
- Графическое отображение открытых портов
- Port forwarding / NAT правила
- Rate limiting на портах (UFW `limit`)

### 3.7 Логи — стриминг и реальный анализ
**Проблема:** `INITIAL_LOGS` — mock. AI-анализ работает, но логи загружаются разово.

**Решение:**
- Убрать mock-данные
- `journalctl -f` через WebSocket — live-стрим логов
- Фильтры: unit, priority, timeframe, grep
- Поиск по содержимому логов
- Экспорт логов (download через SFTP)
- AI-анализ работает с реальным содержимым (уже частично реализовано)
- Автоопределение критических событий (regex patterns для common errors)

### 3.8 Инструменты — полная функциональность
**Проблема:** `INITIAL_CRON_JOBS`, `INITIAL_USERS` — mock. Cron добавление работает, но удаление — нет. Управление пользователями — только просмотр.

**Решение:**
- Cron:
  - Убрать mock, загружать `crontab -l` (или `/etc/cron.d/`)
  - Добавление, редактирование, удаление заданий
  - Просмотр /etc/crontab и /etc/cron.d/
  - Cron-выражение валидатор с предпросмотром следующих запусков
- Пользователи:
  - Добавление/удаление пользователей (`useradd`, `userdel`)
  - Изменение пароля (`passwd`)
  - Управление sudo-правами (`usermod -aG sudo`)
  - Просмотр группы пользователя (`id`, `groups`)
  - SSH-ключи (`~/.ssh/authorized_keys`)
- Системная информация:
  - `sysctl` просмотр и изменение ключевых параметров
  - `uname -a`, `lsb_release`, `dmesg` (последние ошибки)
  - Управление временем (`timedatectl`)

## ЭТАП 4 — UX И ПРОИЗВОДИТЕЛЬНОСТЬ (недели 9-10)

### 4.1 Многопользовательский режим
- Роли: Admin (полный доступ), Operator (управление, без настроек), Viewer (только просмотр)
- RBAC на уровне эндпоинтов и действий
- Audit log — кто что делал, когда
- Приглашение пользователей по email

### 4.2 Управление несколькими серверами
- Группы серверов (теги, категории)
- Пакетные операции (обновить пакеты на всех, перезапустить Nginx на выбранных)
- Сравнение метрик между серверами
- Dashboard с обзором всех серверов (health summary)

### 4.3 Уведомления и алерты
- Настройка порогов: CPU > 80%, RAM > 90%, Disk > 85%
- Уведомления: email, Telegram-бот, webhook
- История инцидентов
- Тихие часы (do not disturb)

### 4.4 Performance
- Lazy loading компонентов (React.lazy + Suspense)
- Виртуализация списков (процессы, логи, файлы)
- Кэширование метрик на клиенте
- Debounce поиска
- Service Worker для офлайн-режима (кешированный UI)

### 4.5 PWA
- manifest.json, service worker
- Установка на телефон как приложение
- Push-уведомления (через VAPID)
- Офлайн-режим для просмот
